# 第 1 章　Linux 与 Arch Linux

一台电脑刚买回来的时候，那些零件本身什么都不会做。处理器在等指令，内存在等数据，硬盘在等读写请求。要把这些冷冰冰的东西变成你能用的机器，中间必须有一层软件来统一调度——这一层就是操作系统（operating system，简称 OS）。

## 操作系统在做什么

把一台电脑想成一家餐厅。硬件是厨房里的灶台、冷库、备餐台；你打开的各种程序，是来点菜的客人。厨房不能谁想进就进、想拿什么就拿什么，否则非打起来不可。所以餐厅需要一个后厨总管：谁先用灶、食材从哪儿出、做好的菜端到哪张桌，都由他统一安排。

操作系统干的就是这件事。它不直接替你写文档、看视频，但它决定哪个程序此刻能用处理器、能分到多少内存、能读写哪块硬盘、能不能联网。任何程序想碰硬件，都得向操作系统提申请，由它代办。这个统一受理申请的机制，叫系统调用（system call）。

操作系统内部又分成两层，这个分工值得先记住。

最里面那层叫内核（kernel）。它直接和硬件打交道，掌管处理器时间怎么分配、内存怎么划分、磁盘和网卡怎么驱动。内核的权限极高，一旦它出错，整台机器可能直接停摆。所以内核被刻意设计得小而克制，只做最必要的调度与隔离。

内核之外的所有东西，统称用户态（user space）。你看到的桌面、浏览器、编辑器、终端窗口，全都活在这一层。它们没有直接操作硬件的权力，想做任何出格的事，都得回头请内核帮忙。这种"内核守门、用户态干活"的结构，好处是隔离：一个浏览器崩了，通常不会把整台机器一起带走。

一句话概括：内核是权力的中心，用户态是生活的地方。

## 发行版：同一台发动机，不同的整车

严格说，Linux 只是一个内核的名字。它由 Linus Torvalds 在 1991 年发起，今天由全球开发者共同维护。但只有内核，电脑是没法用的——你还需要命令行工具、编译器、图形界面、驱动程序、网络配置手段，以及一套能把它们装上、升级、卸载的机制。

内核之外的这些东西，绝大部分来自 GNU 计划和其他开源项目。所以严谨的说法是 GNU/Linux，日常口语里就简称 Linux。

问题在于，把内核和成百上千个软件拼成一套能跑的系统，是一件极其繁琐的活。每个软件的版本要互相匹配，配置文件要写对，出了问题得有人修。于是就有了发行版（distribution，简称 distro）。

可以用汽车打比方。发动机、变速箱、底盘这些东西，都有专门的厂商在做，它们是上游（upstream）——原始开发者，按自己的节奏发布新版本。发行版则是整车厂：选哪款发动机、配什么变速箱、内饰怎么布置、售后网点开在哪儿，都由它决定。同一台发动机，可以装出家用轿车，也可以装出越野车。

发行版的核心资产通常有三样：

- 一个软件仓库（repository），即一台服务器，存着几千个已经编译好、彼此兼容的软件包；
- 一个包管理器（package manager），负责从仓库取回软件、装上、记下它依赖哪些别的软件，以后统一升级或卸载；
- 一套默认配置与一份安装说明，让这套东西能开箱就用。

这里的"依赖"（dependency）值得多解释一句。软件很少孤立存在，一个播放器可能要用到某个解码库，那个库又依赖某个基础运行库。就像装一盏吊灯，除了灯本身，还得有膨胀螺丝和电线。包管理器的工作，就是自动把这些螺丝和电线一并备齐，并在升级时保证它们仍然对得上。

不同发行版在这三样上的取舍不同，于是长成了不同的性格。比较主流的几大家族有：Debian 及其衍生的 Ubuntu、Red Hat 系的 Fedora、openSUSE，以及本章要讲的 Arch Linux。

## Arch 在其中的位置

Arch Linux 于 2002 年由 Judd Vinet 创建，如今由 Arch 社区自身维护。

如果继续用装修打比方，多数发行版交付的是精装房：地板铺好、家电摆好，拎包入住。Arch 交付的是毛坯房，外加一套质量很好的建材和一本极其详尽的施工手册。装成什么样，是你的自由，也是你的责任。

这个定位带来几个直接后果。Arch 的安装过程不会替你做太多决定，分区、选装哪些组件、怎么写配置，都得自己来。装完之后系统里只有你点名要的东西——没有预装的办公套件，也没有替你搭好的桌面环境。想要什么，自己装。

对新手来说这听着像刁难，但对另一部分人来说这正是价值所在：系统里每一层你都认识，出了问题你能一路查下去，而不是对着一堆来路不明的预装软件猜。

## 三条设计原则

Arch 官方把自己的取舍归纳为一组原则，通常称为 Arch 之道（The Arch Way）。其中对使用者影响最直接的是三条。

**简洁（simplicity）。** 这里的简洁不是"界面好看、步骤少"，而是"系统里没有多余的中间层"。Arch 不会给你一个图形化向导把细节藏起来，也不会在你不知情时替你改配置文件。它更愿意只提供一个清晰的机制，让你自己决定怎么用。代价是你要多懂一点，收益是系统里没有你解释不了的东西。

**现代（modernity）。** Arch 紧跟上游，软件包里装的通常就是上游发布的最新稳定版本，而不是被发行版冻结许久、再打上一堆补丁的旧版本。好处是新硬件、新特性来得快；代价是上游的 bug 也会更快到你面前。

**务实（pragmatism）。** 原则归原则，能解决问题才算数。Arch 不会为了某种理念上的纯粹，硬把可用的东西拒之门外；该用的补丁会用，该妥协的地方会妥协。它追求的是"这套东西对开发者有用"，而不是"这套东西在理论上完美"。

三条合起来其实是一句话：Arch 把决定权交给你，同时不承诺替你兜底。

## 滚动更新：没有"大版本"这回事

多数发行版采用固定版本（fixed release）模式。它们定期冻结一次软件版本，打包成一个大版本发布，比如某个年份某个编号。两次发布之间，除安全修复外软件版本基本不动。你在用的是一份被定格的快照，好处是稳定可预期，代价是半年或一年内拿不到新东西。

Arch 不这么干。它采用滚动更新（rolling release）：没有版本号，没有"Arch 25"这样的叫法，只有一个持续流动的软件仓库。你随时同步仓库，就能拿到当下最新的整体状态。系统永远处于"当前"，而不是"某个已发布的版本"。

滚动更新省掉了不少麻烦：不存在"跨大版本升级"这种需要备份、重装、祈祷的大手术；也不存在"文档写的是新版、你手上是旧版"的错位——Arch 的文档与仓库状态始终同步。

但代价是实打实的，而且必须提前知道。

**第一，没有稳定期的缓冲。** 上游发布新版本，经过打包和测试就会进入仓库。你没有"等半年让别人先踩掉问题"的选项，某些更新确实会带来回归问题。

**第二，更新是日常动作，不是年度事件。** 固定版本用户一年更新一次，Arch 用户需要经常同步。长期不更新之后再一次性同步，风险会显著上升。

**第三，绝对不能做部分更新。** 这一点最容易被新手忽视。Arch 的仓库是一个整体，各软件包之间的依赖关系按当前仓库状态对齐。只升级其中某一个包，很可能让整台机器陷入互相不匹配的状态。正确的做法永远是整仓库一次性更新：

```
# pacman -Syu
```

`pacman` 是 Arch 的包管理器，`-Syu` 的意思是同步仓库信息并把系统里所有包一起升级。请把这条命令当成整体，不要拆开只更新单个包。

**第四，你需要读公告。** 少数更新需要人工干预，比如某个配置文件换了格式、某个服务改了默认行为。Arch 会把这些写在更新公告里。更新前扫一眼公告，是使用 Arch 的基本习惯。

## 学 Arch 需要什么心理准备

最后说点实际的。

**你会自己装系统。** 没有人替你一路点"下一步"。分区表写错、引导程序装错位置，都是新手会经历的事。这不是天赋问题，是熟练度问题。

**你会读大量英文文档。** Arch Wiki 是这个发行版最重要的资产，写得极其详尽，且紧跟当前状态。它不假设你懂，但也不哄你。把它当第一手资料用，是这个社区默认的协作方式。

**你会把系统弄坏。** 认真说，这不是失败。Arch 不阻止你做危险操作，也不在你误操作时跳出来挡住你。设计上的假设是：使用者知道自己在做什么，并愿意为自己的操作负责。弄坏了就查文档、进恢复环境、修回来——这个过程本身就是最好的学习。

**你不需要先成为程序员。** 零基础完全可以开始，但你需要愿意动手、愿意追问"这一步到底在干什么"，而不是只求一条能照抄的命令。

**不要把 Arch 当成"进阶版 Ubuntu"。** 它不只是更难装，它是另一种契约：发行版少替你做决定，你多承担一部分责任。接受这个契约，用起来会很痛快；不接受，就会觉得处处别扭。

这套契约值不值得，取决于你想从这台机器上得到什么。如果只是想装好就能用，别的发行版更省心；如果你想弄明白一台电脑到底怎么跑起来，Arch 是一条很直接的路——因为它几乎不藏东西。
