# 第 6 章　学习方法与故障排查

## 一、先把 Arch Wiki 当成手册，而不是教程

Arch Wiki（wiki.archlinux.org）不是一本从头读到尾的书，而是一部可以按需查阅的手册。理解它的组织方式，比记住任何一条命令都重要。

它的基本单位是**页面（page）**。每个页面讲一件事，比如一个软件、一个子系统、一个流程。页面开头通常有一段概述，告诉你这个页面解决什么问题；紧接着是**目录（table of contents）**，列出全部小节。多数页面遵循相似的骨架：安装、配置、使用、故障排查（Troubleshooting）、参见（See also）。看到"Troubleshooting"小节，应该优先跳过去，因为前人踩过的坑通常写在那里。

页面之间靠**分类（category）**和内链连接。页面底部会列出它所属的分类，分类页则是同类页面的集合。正文里的蓝色链接，往往指向你下一步需要读的页面。读到一半发现某个概念不懂，直接点进去，读完再退回来，这是 Wiki 的正常读法。

检索有几个实用技巧。第一，**用英文搜**。英文页面最全、更新最快，中文翻译常常滞后甚至缺失。第二，站内搜索框适合搜主题词（如 `network configuration`），不适合搜长句子。第三，搜报错原文时，用搜索引擎加站点限定，把报错的关键片段放进引号：

```
site:wiki.archlinux.org "failed to mount /boot"
```

第四，页面底部有最后修改时间。如果一段配置说明是很多年前的，要警惕它是否还适用于当前版本。第五，Wiki 不是唯一来源。命令自带的 `--help`、手册页（man page，用 `man 命令名` 查看）、软件自己的上游文档，都是更权威的一手资料。Wiki 帮你定位，一手资料帮你确认。

## 二、报错信息是给你看的，不是给你怕的

大多数报错遵循同一个结构：**谁**在**做什么**的时候，因为**什么原因**失败了。读报错就是把这几个空填出来。

先看第一行和最后一行。第一行通常点明出错的程序和动作，最后一行通常是结论。中间的大段输出往往只是上下文。特别注意报错里出现的**路径**、**单元名**、**包名**、**设备名**，这些是搜索时最有价值的关键词，比"报错了怎么办"有用得多。

区分标准输出和标准错误。正常结果走标准输出（stdout），错误走标准错误（stderr）。把命令的输出重定向到文件时，两者默认分开，排查时更可靠的做法是直接用日志工具看。

命令执行完，可以用退出码判断成败：

```
$ echo $?
```

`0` 表示成功，非 `0` 表示失败。脚本和自动化里全靠这个值判断。

系统层面的日志交给 journal。systemd 把内核、服务、应用的日志汇总在一起，按启动轮次（boot）分组：

```
$ journalctl -b
$ journalctl -b -p err
$ journalctl -u 服务名 -b
```

第一条看本次启动的全部日志，第二条只看错误级别以上，第三条只看某个服务。日志很长时，用 `-p` 过滤级别，比从头翻要快得多。内核自己打印的信息还可以用 `dmesg` 单独看，硬件相关的报错大多在那里。

搜索报错时，**复制完整的一行，连同前后几行上下文**。只搜半句常常搜不到，或者搜到不相关的答案。如果报错里有你机器特有的信息（主机名、用户名、IP、序列号），搜之前先替换成占位符。

## 三、分层排查：从最底下往上查

系统的启动是一条链：固件（firmware）找到引导程序（bootloader），引导程序加载内核（kernel），内核挂载初始内存盘（initramfs），initramfs 挂载真正的根文件系统，然后交给 init 系统（systemd）启动各项服务，最后由服务拉起应用。

这条链上任何一环断了，表现都可能是"开不了机"。所以排查要**按层进行，从下往上**，一层确认通过再查上一层。跳层排查是最常见的浪费时间的方式。

下面是一份可以照着执行的顺序：

1. **确认硬件和固件层**。开机有没有自检画面，硬盘是否被识别。进固件设置或从安装介质启动，用 `lsblk` 和 `blkid` 看分区和文件系统是否还在。
2. **确认引导层**。引导菜单能不能出现，选中项指向的内核和 initramfs 是否存在。
3. **确认内核与 initramfs**。内核能不能加载，initramfs 里是否包含根分区所需的驱动。近期升级过内核却忘了重建 initramfs，症状就是卡在这一层。
4. **确认根文件系统**。根分区能不能挂载，`/etc/fstab` 里的条目是否与实际分区一致。
5. **确认 init 系统**。systemd 有没有起来，哪些单元失败了：

```
$ systemctl --failed
$ systemctl status 单元名
```

6. **确认服务层**。依赖网络、数据库、显示管理器的服务，是否因为更底层的服务没起来而连带失败。
7. **最后才是应用层**。单个程序崩溃，前面的层通常都是好的。

每一层都问同一个问题：**最近改了什么**。新装的包、改过的配置文件、升级过的内核，是绝大多数故障的直接原因。时间线比猜测可靠。如果记不清，包管理器的日志和文件的修改时间可以帮你还原。

## 四、五类常见致命错误

**第一类：引导链断裂。** 症状是开机直接进固件界面，或者停在引导菜单后黑屏。常见原因是升级内核后没有重新生成 initramfs，或者引导程序的配置文件没有更新。确认方法是从安装介质启动并挂载根分区，检查 `/boot` 下的内核与 initramfs 文件是否成对存在。修复需要进入 chroot 环境，重新生成 initramfs 并更新引导配置。

**第二类：根分区写满。** 症状是登录后什么都做不了，日志里满是"设备上没有空间"（No space left on device）。日志文件、包缓存、下载目录是常见的增长点。用 `df -h` 看各分区占用，再逐层定位大目录。注意给根分区留出余量，写满之后连日志都写不进去，排查会更困难。

**第三类：权限与所有者被误改。** 典型场景是在根目录下执行了递归的权限修改，或者在错误的位置改了属主。症状五花八门：`sudo` 报错、服务起不来、图形界面登录失败。这类问题的麻烦在于波及面广，报错本身不指向真正的原因。确认方法是检查关键目录的属主和权限是否符合预期；修复要靠包管理器校验文件完整性，把被改坏的文件恢复回来。

**第四类：包管理器状态损坏。** 包括部分升级（只升级了某个包而没有整体升级）、数据库被锁、依赖关系断裂。症状是安装或升级时报依赖冲突，或者系统里一半是新版本一半是旧版本。原则很简单：升级永远整体做，不要单独升级某个包。数据库被锁时，先确认没有别的包管理进程在运行，再处理锁文件。

**第五类：网络与域名解析不通。** 这一类本身不致命，但它会让你失去自救能力，所以必须单独列出来。症状是包管理器连不上镜像站，或者能 ping 通 IP 却打不开域名。先分层确认：网卡有没有拿到地址，网关通不通，域名解析是否正常。把这几个问题分开测，才能知道故障出在链路、路由还是域名解析（DNS）。

## 五、什么时候该重装

重装系统不是失败，是一次成本决策。判断标准只有一个：**修复的预期时间，是否明显超过重装的预期时间**。

倾向于重装的信号：文件系统损坏到无法修复；同一台机器上同时存在多个互不相关的故障；系统被大量手工修改过，已经没人说得清当前状态；你需要在很短时间内恢复一台能用的机器。

倾向于不重装的信号：故障只影响单个服务或单个程序；问题出在配置而不是系统本身；你还能从安装介质启动并挂载根分区。绝大多数引导问题和服务问题都属于这一类，修比重装快。

决定重装之前，先备份。至少包括：`/home` 下的个人文件、`/etc` 下的配置文件、已安装软件包的清单，以及浏览器和密钥环里那些不方便重建的数据。包清单可以导出成文本，重装后照着装回去：

```
$ pacman -Qqe > pkglist.txt
```

如果系统还能启动，先把清单和配置拷到外部存储。如果已经起不来，就从安装介质挂载分区再拷。备份这一步省不得，重装可以重来，数据不行。
