# 第 4 章　软件包与依赖

## 先看看源码安装

大多数开源项目的主页上都挂着一个源码包，通常是压缩后的归档文件。下载、解压，里面的结构大同小异，跟着三步走：

```text
$ ./configure
$ make
$ make install
```

第一步叫配置（configure）：检查你的系统里有没有它需要的东西——编译器、某个库、某个头文件，然后把检查结果写成一个构建文件。第二步编译（make）：按构建文件里的规则，把成千上万个源文件翻译成机器能执行的东西，这一步常常要等上几分钟到几十分钟。第三步安装（make install）：把编译出来的程序、库和文档复制到系统目录里。

看起来不难。但装完第一个之后，麻烦才开始。

`make install` 干的事本质上就是复制文件。它不会告诉系统"我装了某某软件"，也不会在任何地方留下清单。于是你很快会遇到几件事：

- 想卸载，没有卸载命令。只能翻回源码目录试试 `make uninstall`，而很多项目根本没写这条规则；就算写了，也只认得当初安装时的那份配置。
- 想升级，得把三步重来一遍。新版本又依赖了新的库，`configure` 会中途停下，告诉你找不到某某。你再去为那个库重复上面所有步骤，一层套一层。
- 想知道某个文件是谁放进来的，说不清。它和你以前装的软件混在同一个目录里。
- 想知道自己到底装了哪些东西，同样说不清。

这就是依赖地狱（dependency hell）的雏形：软件越来越多，彼此要求的版本还会互相矛盾，而系统里没有任何一个角色掌握全局信息。谁装的、谁依赖谁、能不能删，全靠你的记忆。

## 包管理器在管什么

包管理器（package manager）首先要解决的就是"没人记账"这件事。

它的第一个动作，是把"软件"变成一个边界清楚的东西，叫软件包（package）：一个归档文件，里面装着编译好的程序和库，外加一份描述信息（metadata），写明这个包叫什么、版本是多少、装了哪些文件、依赖哪些别的包。你在源码安装里手打的那三步，打包者已经在自己的环境里替你做完了。

有了这个边界，包管理器才能做四件事：

- **安装与卸载**。卸载时按清单把文件逐个删掉，不多删也不漏删。
- **记账**。装了什么、装的是哪个版本、某个文件属于哪个包，都写进一份本地记录。
- **解析依赖**。装一个包之前，先算出它还需要哪些包，一次性备齐。
- **统一升级**。所有包按同一份仓库信息一起推进，让彼此的版本保持对得上。

包里的文件也不是随便丢进系统，而是按第三章讲的目录习惯放在固定位置：程序进 `/usr/bin`，库进 `/usr/lib`，配置文件进 `/etc`。正因如此，一个包在系统里留下的痕迹是可枚举的——这是记账能成立的前提。

## 仓库：别人替你编译好的地方

仓库（repository，常简称 repo）是一台服务器上的一组软件包，由发行版维护。Arch 的官方仓库按用途分成几个，各自装着一批由官方打包者维护、签名过的包。

从用户角度看，仓库省掉的是编译。从发行版角度看，仓库真正提供的是**一致性**：这些包是在一套约定的环境里、按同一批依赖版本编译出来的，装到一起就能跑。你自己编译的那份二进制，落在这个约定之外。

仓库还有个容易被忽略的作用：集中信任。每个包由打包者签名，你的系统只接受持有对应密钥的人打出来的包。所以"从仓库装"这个动作包含的不只是下载，还有一次签名校验。

## 数据库：系统对自己知道多少

包管理器把账记在两个地方，理解这两个地方的区别，后面很多现象就顺了。

一处是**本地数据库**（local database），记的是"这台机器上实际装着什么"，位于 `/var/lib/pacman`。你问系统"这个文件是谁装的""我是不是装过某个包""这个包依赖什么"，读的都是它。

```text
$ pacman -Qo /usr/bin/vim
$ pacman -Qi vim
```

第一行问的是某个文件属于哪个包，第二行问某个已安装包的信息。这类查询之所以能立刻回答，正是因为安装时写下了账。

另一处是**同步数据库**（sync database），是仓库索引在你机器上的一份副本。它记的是"仓库里有什么、什么版本、依赖谁"，不表示你已经装了。搜索和查询仓库里的包读的是它：

```text
$ pacman -Ss 关键词        # 关键词替换成你要找的东西
```

同步数据库是从仓库下载来的，会随着你每次同步被替换。它只是一份目录，不是文件本身。这个区别很重要，下面讲滚动更新时会用到。

## 依赖解析：一张不断变动的图

把包和依赖画成图，每个包是一个点，依赖是一条有向的边。装一个包，就是要把以它为起点的整片可达区域都找出来。

难点在于这张图不是静态的。同一份依赖可能同时被好几个包需要，各方的版本要求还可能互相冲突；有的包能顶替另一个包的角色（提供同样的能力，但实现不同）；有的包之间则不能共存于同一套文件布局之下。所以依赖解析不是"查一张表"，而是一次求解：在满足全部约束的前提下，挑出一组能同时装上的版本。

这也是为什么包管理器报错时，说的往往不是"找不到包"，而是"无法满足依赖"或"某两个包冲突"。它在告诉你：这件事在你的系统当前状态下无解，需要你先做取舍。

## 滚动更新：仓库是一个整体

第一章提过 Arch 采用滚动更新（rolling release），这里要补上它对包管理器提出的额外要求。

在固定发布的发行版里，一次大版本发布就是一个被冻结的包集合，所有包的依赖都在这个集合内部对齐。Arch 没有这样的集合——仓库在持续被替换，任何时刻它都代表"当前最新的整体状态"。于是有了一条推论：

**仓库里所有包的依赖关系，是按整份仓库对齐的。** 只要你同步了仓库索引，就应该把所有已装软件一起升到这份索引对应的状态。只升其中一部分，就等于把系统的一半锁在旧状态、一半推到新状态，而这两半之间的接口并没有人保证。

下面的写法就是典型的错误操作：

```text
# pacman -Sy 某个包
```

`-Sy` 只刷新索引，不带升级。它的结果是：你的索引已经很新，已安装的软件还是旧的，接着再装一个新包，新旧两套依赖就被拼到一起了。Arch 把这种情况叫部分更新（partial upgrade），是官方明确劝阻的。要装东西，就把"同步 + 全体升级"当成一个不可拆开的动作：

```text
# pacman -Syu
```

滚动模型的另一面是：更新是日常动作，不是年度事件。长期不同步之后一次性追上，中间跨越的状态越多，出问题的概率越高。官方偶尔也会要求人工介入——比如某个包的配置文件格式变了，需要你手动处理。这些都会写进更新公告里。

## AUR：一份配方，不是一台仓库

Arch 用户仓库（Arch User Repository，AUR）经常被误解。名字里虽然有 repository，它和官方仓库不是一类东西。

官方仓库里放的是**编译好的包**。AUR 里放的是**构建配方**：一份叫 PKGBUILD 的脚本，加上配套文件，说明从哪个上游地址取源码、怎么编译、装到哪儿。AUR 不提供二进制文件，也没有人替你在服务器上编译。

所以"从 AUR 装东西"实际是两步：取回配方，在你的机器上现场构建，再装成品。社区写的若干助手工具（例如 `yay`、`paru`）只是把这两步串起来做得顺手些，它们不是官方组件，Arch 官方也不为它们背书。

AUR 的价值很直接：官方仓库不可能收录所有软件，尤其是一些小众工具、上游闭源的东西、或打包者不认为该进官方仓库的软件。它把"打包"这件事开放给了社区。

风险同样直接，而且有几层：

- **没有人在替你把关成品。** 官方仓库的包有打包者签名，AUR 的配方只有作者和投票记录。配方里能写任意命令，构建过程在你的机器上以你的身份运行。所以装之前看一眼 PKGBUILD，是个应有的习惯，而不是多疑。
- **配方会过期。** 上游换了构建系统、改了依赖，配方没跟上，构建就会失败。这种失败和你的系统没关系，是配方本身旧了。
- **版本节奏不由官方约束。** AUR 包通常跟着上游走，而库的升级会让旧二进制失去兼容。滚动更新之后，AUR 里装的东西常常需要重新构建一次才能继续用。
- **可能撞车。** AUR 包和官方包装了同一种东西，就可能互相覆盖文件或产生冲突。

把这些放在一起，AUR 的定位其实很清楚：它是官方仓库的补充，不是官方仓库的替代，也不在支持的范围内。能用官方包解决的，用官方包。

## pacman 的取舍

`pacman` 是 Arch 的包管理器。回头看，它的性格和第一章讲的 Arch 之道是一致的：只提供机制，不替你下判断。

具体表现为几条一以贯之的选择：

- **只做被要求的事。** 它不弹窗、不自动确认、不猜你的意图。要装就装，要删就删，不问第二遍。
- **记账清楚，但不代为解释。** 装了哪些文件、谁依赖谁，全都能查；但它不会主动告诉你"这个操作可能影响其他包"。
- **不自动清理依赖。** 删一个包，默认只删它自己。它顺带用到的库会留在系统里——因为那些库可能还有别的东西在用，判断权交给你。想连不再需要的依赖一起删，得明确说出来。
- **不替你合并配置。** 更新时如果你的 `/etc` 下某个文件被改过，它会保留你的版本，另外放一份新版本在旁边，由你决定怎么合。
- **不在出错时兜底。** 下载过的包会留在缓存目录里，所以回退到旧版本是可能的；但回退这个决定，仍然要你自己做。

这套取舍的代价，就是你得知道自己敲的命令意味着什么。好处是，系统里几乎不存在"不知道为什么变成这样"的地方——包这一层尤其清楚：装了什么、从哪儿来、被谁依赖，全都有账可查。

第二册会把这本账翻开来细看：数据库里到底记了什么、依赖冲突时怎么读输出、AUR 的配方怎么写、系统滚坏了怎么退回去。前提是这一章的东西已经不再陌生——包是被管理起来的文件集合，仓库是别人替你编译好的一致集合，更新是一个整体动作而不是零散操作。
