# 第 5 章　系统与服务

## 开机之后，谁在干活

按下电源键以后，主板固件把控制权交给引导程序，引导程序加载内核。内核做完自己的事——初始化硬件、挂载根文件系统——就会启动它找到的第一个用户空间程序，并把它的进程号（PID）定为 1。

这个数字很要紧。内核本身不管服务，也不管网络和登录，它只负责把第一个进程拉起来。此后系统上所有"不用人盯着也一直在跑"的东西，都是这个进程及其子孙在承担。这个角色叫作 init，取自 initialization（初始化）。

历史上各家发行版用过不同的 init。Arch 早期用的是 SysV init，后来换成了 systemd。systemd 自己就是那个 PID 1，同时兼作服务管理器。想知道当前系统上是谁在当 PID 1，可以看进程表：

```bash
$ ps -p 1 -o comm=
systemd
```

顺带记一个词：后台常驻、不需要人交互就能自己运行的程序，叫作守护进程（daemon）。systemd 的核心职责就是把这类守护进程按时拉起来、看着它们、必要时关掉。

## 单位：systemd 眼里的万物

systemd 不把系统想成一堆启动脚本，而是想成一堆"单位"。单位（unit）是它管理的最小对象，每个单位由一个配置文件描述，文件名后缀说明它属于哪种类型：

- `.service`：一个后台服务，最常见的一种
- `.socket`：一个被监听的端口或套接字，有人连上来时才唤醒对应服务
- `.timer`：定时触发器，作用类似传统的 cron
- `.mount` 与 `.automount`：挂载点
- `.path`：监视某个文件或目录的变化，变了就触发动作
- `.target`：一批单位的集合，下一节再说

单位文件主要来自两个地方：`/usr/lib/systemd/system/` 放软件包自带的，升级时会被覆盖；`/etc/systemd/system/` 放管理员自己写的，优先级更高，同名会盖住前者。这种"系统目录加本地目录、后者覆盖前者"的安排在 Arch 里反复出现，值得先记住。

也正因为如此，想改某个单位的行为，不要去动 `/usr/lib` 下面的文件，正确做法是在 `/etc/systemd/system/` 里放一个同名文件，或者建一个形如 `名称.service.d/` 的目录，把要改的几行写进去。后者叫 drop-in，注意力集中、不容易和升级冲突。`systemctl edit 名称.service` 会自动帮你建好这个目录并打开编辑器，`systemctl cat 名称.service` 则把上层文件和所有 drop-in 拼在一起显示出来，改之前先看一眼它到底长什么样。

有时候某个服务被别的单位当依赖顺手拉起来，你并不想让它跑。这时 `# systemctl mask 名称.service` 把它彻底封掉——它会被链接到 `/dev/null`，即便有人想启动它也无从下手；解除用 `systemctl unmask`。比起 `disable`，`mask` 是更硬的封锁。

## 目标：一批单位被打包

系统的启动过程可以拆成阶段：先是文件系统可用，然后网络就绪，最后才轮到图形界面。systemd 用目标（target）来表示"系统现在应该处在哪个状态"。

target 自己几乎不干活，它更像一个标签或者一个组。启动一个 target，等于启动它名下的一批单位。常见的几个：

- `multi-user.target`：多用户、有网络，但没有图形界面
- `graphical.target`：在 `multi-user.target` 的基础上再拉起显示管理器
- `rescue.target`：救援模式，只起最基本的服务
- `poweroff.target` 与 `reboot.target`：关机与重启

老 SysV 时代有个"运行级别"（runlevel）的概念，现在基本被 target 取代，systemd 保留了一点兼容映射。默认要进哪个 target，可以查也可以改：

```bash
$ systemctl get-default
graphical.target
# systemctl set-default multi-user.target
```

开机时 systemd 直奔默认 target，顺带拉起整条依赖链。所谓"服务开机自启"，机制就在这里。

## 启停与开机自启

日常打交道最多的就是这几个动作，先把它们分清：

- `start` / `stop`：现在启动、现在停止
- `restart`：停掉再起来；`reload`：不中断服务，只让它重读配置
- `disable` / `enable`：下次开机是否自动启动
- `status`：看它现在怎么样

最容易被弄混的是 `start` 和 `enable`。`start` 只影响眼下这一次运行，重启机器就没了；`enable` 只影响下次开机，不会立刻把服务跑起来——除非加上 `--now`。

```bash
# systemctl status 名称.service
# systemctl start 名称.service
# systemctl restart 名称.service
# systemctl enable 名称.service
# systemctl enable --now 名称.service
# systemctl disable 名称.service
```

`status` 的输出值得逐行看明白。Loaded 一行说明单位文件从哪儿来、是否处于 enabled 状态；Active 一行是关键，`active (running)` 表示正在跑，`inactive (dead)` 表示没在跑，`failed` 表示启动失败了。Active 下面的几行是最近几条日志，通常够判断问题出在哪，末尾还会提示你用 journalctl 去看更多。

依赖关系和排错时常用的几条：

```bash
$ systemctl list-units --type=service      # 内存中已有的服务
$ systemctl list-unit-files --type=service # 磁盘上有哪些，各自是否自启
$ systemctl --failed                       # 当前失败的单位
$ systemctl list-dependencies 名称.service # 它依赖谁
```

服务起不来时，先别急着重启一遍，用 `status` 和日志看清原因，往往比反复重试省时间。

## 日志在哪里

systemd 自带一个日志服务 systemd-journald，它收集内核消息、各个服务的标准输出与错误输出，以及从别处转来的日志。查询工具是 `journalctl`。

日志落在哪儿分两种情况。如果 `/var/log/journal/` 这个目录存在，日志会写到磁盘，重启后还在；如果它不存在，日志就只写到内存里的 `/run/log/journal/`，关机即失。Arch 默认不建这个目录，所以想要跨重启保留日志，自己创建一次即可：

```bash
# mkdir -p /var/log/journal
# systemctl restart systemd-journald
```

常用查询：

```bash
$ journalctl                # 全部日志，从旧到新
$ journalctl -b             # 只看本次启动
$ journalctl -b -1          # 上一次启动
$ journalctl -u 名称.service # 只看某个服务
$ journalctl -f             # 持续跟踪新日志
$ journalctl -k             # 只看内核消息
$ journalctl -p err -b      # 本次启动中优先级为 err 及以上
$ sudo journalctl --disk-usage   # 日志占了多少磁盘
```

`--since` 与 `--until` 可以按时间切片，写法比较宽容，`"1 hour ago"`、`"yesterday"`、`"2024-01-01 10:00:00"` 都认。把这些选项组合起来，比如 `journalctl -u 名称.service -b --since "10 min ago"`，就是排查"刚才那个服务为什么挂了"的标准动作。

日志有上限，不会无限长大，默认会在磁盘占用过多时丢掉最旧的部分。确实需要腾空间时，可以手动清到某个尺寸：`# journalctl --vacuum-size=500M`。

权限方面，普通用户默认只能看到自己的日志。要读全系统的日志，需要是 root，或者把自己加进 `systemd-journal` 组：

```bash
# usermod -aG systemd-journal 用户名
```

除了 journal，`/var/log/` 下还有一些由程序自己写的纯文本日志。其中 `pacman.log` 记录了软件包安装、升级、卸载的全部历史，想知道"这个包是哪天装进来的"翻它就行。

## 用户、组与 sudo

系统里每个进程都带着一个用户身份在跑。用户用 UID 标识，root 的 UID 固定是 0，拥有绕过一切权限检查的能力；普通用户的 UID 一般从 1000 往上排。

用户信息分散在三个文件里：`/etc/passwd` 记录用户名、UID、主组、家目录和登录 shell，任何用户可读；`/etc/shadow` 存密码哈希，只有 root 能读；`/etc/group` 记录组和组成员。

组（group）是把权限打包分发的手段——进了某个组，就继承这个组拥有的权限。每个用户有一个主组（primary group），此外还可以属于任意多个附加组（supplementary group）。加入 `wheel` 组之所以能让人用 sudo，原因就在这儿。

查看与增删：

```bash
$ id                    # 自己的 UID、主组、附加组
$ groups                # 自己属于哪些组
# useradd -m -G wheel 用户名     # 建用户，-m 才会创建家目录
# passwd 用户名                  # 设置密码
# usermod -aG 组名 用户名        # 追加组
# userdel -r 用户名              # 删用户并一并删掉家目录
```

`usermod -aG` 里的 `-a` 不能省。少了它，追加就变成了覆盖，用户原有的附加组会被整条替换掉，很容易把刚配好的权限弄丢。

sudo 解决的是"临时借 root 权限做一件事"的问题。它要求输入的是自己的密码，而不是 root 密码；相对的，`su -` 是切换到 root 并需要一个完整的 root 会话，要输 root 的密码。日常操作更推荐前者，因为它只给一条命令提权，事后自动收回。

sudo 的规则写在 `/etc/sudoers` 里。编辑它必须用 `visudo`，因为 visudo 会在保存前做语法检查——直接编辑留下语法错误，可能让 sudo 彻底不可用。更稳妥的做法是不动主文件，而在 `/etc/sudoers.d/` 下新建一个单独文件：

```bash
# visudo -f /etc/sudoers.d/10-wheel
```

文件里允许 wheel 组做任何事的那一行长这样：

```
%wheel ALL=(ALL:ALL) ALL
```

开头的 `%` 表示这是组名，不是用户名。这一行的读法是：wheel 组里的所有人，在任何主机上，可以以任意用户身份运行任意命令。Arch 的默认 sudoers 里这条规则是注释掉的，需要自己取消注释，或者写进 `sudoers.d` 里。

配置生效以后，`sudo -l` 会列出你当前被允许执行的命令，改完规则不确定有没有生效，用它可以自查。偶尔需要连着做几件需要 root 的事，`sudo -i` 会给你一个临时的 root 登录 shell，退出即回到自己——比在每条命令前面加 sudo 省事，但仍要记得及时 `exit`。

## 读懂这些输出

现在再打开一个终端，`systemctl status` 的输出不再是黑箱：Loaded 告诉你单位文件从哪来、是否开机自启，Active 告诉你它现在跑没跑，下面几行是它最近的日志。`journalctl -u` 和 `journalctl -b` 则把时间轴拉出来，让你看到某个服务在某个时刻具体说了什么。

把这条链记住，剩下的都是查：内核拉起 PID 1，PID 1 是 systemd，systemd 按 target 组织起一批单位，每个单位背后是一个守护进程；这些进程的输出统一汇进 journal；而谁能对它们做什么，由用户、组和 sudo 规则决定。这一套东西本身不复杂，只是名字多。名字认全了，后台就不神秘了。
